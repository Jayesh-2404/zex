# Zex Project Status - VERSION_20263107

## Current Project Status

Zex is currently a backend-only exchange-style service. The project has an Express API, a separate TypeScript matching engine, Redis messaging between the API and engine, and Postgres persistence for trades, candles, open orders, and idempotency records.

The core backend is implemented and builds successfully. The engine test suite also passes.

## Verified On This Version

- API TypeScript build passes with `npm.cmd run build` from `api/`.
- Engine TypeScript build passes with `npm.cmd run build` from `engine/`.
- Engine tests pass with `npm.cmd test` from `engine/`.
- Test result: 21 passing tests, 0 failures.

## Completed Features

- Express API service on port `3000`.
- Redis-backed request and response flow between API and engine.
- Separate matching engine process.
- Price-time priority order book.
- Buy and sell order matching.
- Partial fill handling.
- Open order depth snapshots.
- Order cancellation.
- Owner check for cancellation so another user cannot cancel someone else's order.
- Market depth endpoint: `GET /api/v1/depth?symbol=SOL_USDC`.
- Tickers endpoint: `GET /api/v1/tickers`.
- Klines endpoint: `GET /api/v1/klines`.
- Create order endpoint: `POST /api/v1/order`.
- Cancel order endpoint: `DELETE /api/v1/order/:orderId`.
- Basic request validation for market format, positive price, positive quantity, side, user id, time range, and idempotency key format.
- Postgres schema for trades.
- Postgres schema for `1m`, `1h`, and `1w` klines.
- OHLCV candle aggregation from fills.
- Conflict-safe kline upserts.
- Durable open-order snapshots in Postgres.
- Engine startup recovery from stored open orders.
- Create-order idempotency using `Idempotency-Key`.
- Idempotency conflict detection when a key is reused with a different request.
- Duplicate create-order retry response replay from the command journal.
- Docker Compose setup for Redis and Postgres.
- Project notes and backend resume story in `docs/PROJECT.md`.

## Current Architecture

- `api/`: Express API layer.
- `engine/`: Matching engine, order book, persistence logic, and tests.
- `db/init/`: Postgres initialization SQL.
- `docs/PROJECT.md`: Existing project notes, next work, and frontend plan.
- `docker-compose.yml`: Local Redis and Postgres services.

The API sends commands into Redis. The engine consumes those commands, mutates the in-memory order book, persists the important state to Postgres, and publishes a response back to the API.

## Main Risks Still Open

- Redis queue/pubsub delivery is simple and may need stronger delivery guarantees for production.
- The order book is in memory, so recovery depends on snapshots and command journal behavior.
- The command journal currently handles completed idempotent create-order responses but is not yet a full event-sourcing or pending-command recovery system.
- There is no balance/account ledger yet, so orders are not financially constrained.
- There is no authentication or authorization layer beyond the `userId` fields supplied by the caller.
- There are no real-time client streams yet, so a frontend would need polling until streams are added.
